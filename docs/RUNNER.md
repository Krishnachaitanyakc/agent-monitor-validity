# Stage runner

`scripts/run_stage.py` runs every stage one way: the request layer builds both bodies, [spend.py](../judge/spend.py) reserves each call on a ledger, and the existing dispatcher sends A1, A2, A3, then B1. Standard library only; the docstring shows the commands.

## Stages

| Stage | Cases | Slots | Guard | Budget |
|---|---|---|---|---|
| P1 | up to 5 development cases | A1 to A3, B1, cached | `dev_only` | pilot, $95 for P1 to P3 |
| P2 | one prompt pass, up to 20 traces | A1, B1, uncached | `dev_only` | pilot |
| P3 | frozen pass, up to 20 tasks | A1 to A3, B1, cached | `dev_only` | pilot |
| EVAL | the frozen panel | A1 to A3, B1, cached | `pre_join` | evaluation, $285 |

A stage starts only after the previous stage's complete `report.json`, in the same mode, and a passing reconciliation after that stage's last call. P3 and EVAL also refuse a rubric whose status is not `frozen`. EVAL needs `--panel-manifest`, its recorded `--panel-sha256` and `--freeze-tag`: the manifest must match the hash, name the tag and config hash, and list the given packs in order, with the code at the tag and a clean tree. It must also hold `p3_run_id`, the `run_id` from the `run.json` of the run root whose P3 it was frozen after, and EVAL refuses any other run root: a fresh one gets a new random ID, so its own short P3 cannot stand in for the real one. EVAL also refuses a P3 of its run that sent no call, since a pilot stage whose only case is ineligible is complete and nothing would have run under its configuration. `--b-model` picks judge B's model, `gpt-6-sol` or its first fallback `gpt-6.1-sol`; the model is part of the configuration hash, so a fallback is a configuration change, not a code edit. `run.json` fixes the run's mode, study workspace and OpenAI project at its first stage, and every later stage must give the same ones. A resumed stage also keeps its packs, configuration and ledger; a finished one never reruns.

A pilot stage records an ineligible case with its reasons and goes on. Eligibility is settled before the panel is frozen, so in EVAL an ineligible task is an unexpected failure: it writes an `ineligible_frozen_task` halt and the stage stops. The task does not count as ended and N stays the manifest's, so the report cannot be complete without its judgments. A note does not drop the task, and the gate is applied again on resume.

The dispatcher takes all four slots or, for prompt development, A1 and B1 only; any other set is refused. `run_stage` runs only the fake transport in fake mode and only the HTTPS transport in paid mode, on a ledger of the same mode.

## Development allocation

[ALLOCATION_RECORD.md](ALLOCATION_RECORD.md) holds the study's real draw, with its inputs and hashes, and the record of which of its tasks were used before the draw.

`scripts/build_dev_table.py table` writes the table from two label-free counts files, the task mapping and the eligible panel, leaving out AssistantBench and image-goal tasks. A task's template overlaps the panel when it holds a WebArena or VisualWebArena panel task. The command prints counts only, and a refusal names no panel task.

`scripts/draw_allocation.py` fixes which development tasks each pilot stage may use. It takes a JSON table of development tasks with exactly the fields `task_id`, `benchmark`, `template_overlaps_panel` and `family`, P1's five task IDs and a seed, and it reads no label. The rule, in order:

1. P1's five tasks leave the pool.
2. From the tasks whose template does not overlap the panel, 15 are drawn by benchmark: WebArena 8, VisualWebArena 1, WorkArena 6. The one WorkArena task whose family contains `infeasible` takes one of the six, unless it is already in P1.
3. P2 is P1's five plus the 15.
4. P3 is 20 tasks from the remaining task IDs of the whole table after P2.

One draw sorts its stratum's task IDs, gives each the next `random()` value of `random.Random(S)`, sorts by that value and takes the first ones needed. S is the big-endian integer of SHA-256 over `<seed>:<stratum>`, where the stratum is the benchmark name, or `p3` for P3. Only `random()` is used, since Python keeps its sequence for a given seed across versions and makes no such promise for `shuffle` or `sample`. The output holds `p1`, `p2`, `p2_new`, `p3`, `development` (every task ID of the table, drawn or not), the seed, the rule in words, the counts by benchmark and a SHA-256 over its canonical content. It is written once and its lists are sorted, so the same input gives identical bytes. The draw is refused when a stratum is short, the table has duplicates or an ID that is not normalized, the counts do not total, or a P1 task is missing from the table.

`run_stage.py run --allocation` names that file, which must be outside the repository. Paid mode needs it at every stage, and fake mode takes it when given. Paid mode also needs `--allocation-sha256`, the file's `sha256` field as recorded in the plan or the approval note, the way `--panel-sha256` names the manifest. The file's own hash shows only that it was not edited after it was written, so paid mode also refuses a file that is not the study's draw: seed 169, the rule in words, sizes 5, 15 and 20, the quotas, counted from the task IDs as well as from the file's own counts, and P1 apart from the 15. Fake mode compares a hash when one is given and leaves the rest to the draw, so a rehearsal can use a smaller allocation. A trace maps to its task through the `task_id_normalized` field of its provenance record, the ID the split table uses. That field is tied to the trace when the records load: the trace key must be the hash of the record's `trace_id`, `trace_id` must end in the raw `task_id`, and the normalized ID must be the raw one's. Before a run folder is made or anything is sent, the runner refuses:

- a file that fails its own hash, holds an ID that is not normalized, has a P2 that is not P1 plus the 15, has a P3 that overlaps P2, or has a development list that leaves out a task of P2 or P3;
- a P1 trace whose task is not in `p1`, a P2 trace not in `p2`, or a P3 trace not in `p3`;
- in P2, a task of `p1` when the rubric's SHA-256 is the one P1 recorded in its `stage.json`, since the first five go out again only after a rubric change;
- a trace whose normalized task ID is missing or not in the split table's form, a non-empty lower-case string with no space that normalizing leaves unchanged;
- in P3 and EVAL, more than one trace of a task, since P3 is 20 tasks and the panel unit is one trajectory per task;
- in EVAL, any panel task in `development`, drawn or not, since every development task stays out of evaluation.

EVAL in paid mode also loads only provenance records of the test split, which covers the development tasks outside the table, the image-goal and AssistantBench ones. Fake mode leaves the split open, so a rehearsal can use other records.

Once the previous stage's report is checked, an allocation other than one that any stage in the same mode recorded, in this run root or any run root beside it, is refused too, so a fresh run root cannot use another. The frozen panel manifest names the allocation in `allocation_sha256`, and EVAL refuses any other. Stage sizes stay caps, so a stage may run fewer tasks than its list holds. `stage.json` records the allocation's SHA-256, and a resumed stage must give the same one.

The panel leaves out every task in a template that a prompt task used. `scripts/build_dev_table.py exclusion` derives those templates from `p2` and the task mapping and writes the record that the frozen manifest carries as `template_exclusion`: the templates, N before, the tasks removed, N after and the allocation's hash. EVAL refuses a manifest with no such record, one whose counts do not add up or leave fewer tasks than the panel holds, one made under another allocation, a task that names no `template`, and a task whose template the record removes. The panel builder that writes the manifest is not in this repository yet.

EVAL's configuration hash must be the one P3 ran under, read from P3's `stage.json`, in fake and paid mode alike. A difference is refused unless `--config-change-note` names a non-empty file outside the repository that declares it; `stage.json` keeps the note's text and SHA-256 with P3's hash, and a resumed stage must give the same note. A note given when nothing differs is refused, and only EVAL takes one. The frozen-rubric checks of P3 and EVAL are separate and still apply.

## Gates

`progress.json` after every trajectory, and `report.json` once every case has ended, show each slot's invalid share by outcome class, the cache hit share of A2 and A3, spend and projected cost against the cap, calls that reached the 32,000-token output cap, halts with their correction notes, and B's capability check. They are for review only: none selects a judge, and a refusal never triggers a fallback. EVAL's report is complete only after a passing reconciliation that follows its last call: reconcile, then run the same command again to write it.

## Spending rules

- **Reserve.** r = (I × 1.02 + 256) × p_in × 1.25 + 32,000 × p_out: $0.47 at 60,000 input tokens, $0.58 at 100,000. I is the provider's own pre-send count, described under [token counts](#token-counts); twice the request layer's estimate is used in fake mode only, when no count is given. The 1.25 prices all input as a cache write. The ledger header keeps the SHA-256 of the price table, the modifiers, these reservation constants, the request layer's output cap and the source of the functions that compute a reservation, so a code change to any of them refuses a resumed ledger.
- **Admit.** A call goes out only if settled spend, open and held reservations and r stay at or below the cap; otherwise a `spend_cap` halt is written and nothing is sent. A note does not raise the cap. A trajectory whose B request is counted above 272,000 input tokens is refused before its first call (`long_context`), so A1 to A3 are not sent for a B1 that would be refused; the refusal applies again on every resume.
- **Settle.** From the attempt record: a complete response at its reported usage; an Anthropic error response at $0, since Anthropic does not bill failed requests. An OpenAI error that the response does not settle, whose billing is unverified, holds the full amount until a passing reconciliation establishes its cost, as described under [reconciliation](#restart-and-reconciliation): an error status, an error event in a stream, a `response.failed` that does not report its usage in full, or an error body whose status was not kept. No response, a cut stream, an Anthropic error in a stream, an Anthropic stream whose `message_delta` did not report final usage, incomplete usage, or a response whose pricing raises holds the full amount for good. A call that settles above its reservation halts the stage once its trajectory finishes; the cap still counts actual settled spend. That halt is recorded even when another halt ends the same trajectory, and at start for any such call left without one by a stop.
- **Price modifiers.** A complete response that shows a documented modifier settles at the larger of its reservation and its cost under the modifier: A's `inference_geo` `us` (1.1x every token), A's one-hour cache writes ($4 per million), B's cached input ($0.20, or $0.10 on `gpt-6.1-sol`) and cache writes (at the 12-hour rate, 2.5x input), B input above 272,000 tokens (2x input and cache, 1.5x output), and B's `flex`, `priority` and `ultrafast` tiers (0.5x, 2x, 6x). A modifier with no documented price, such as an A tier other than `standard`, holds the full reservation. The dispatcher also halts on each of these responses: an A region other than `global`, an A tier other than `standard`, A one-hour cache writes, a B tier other than `default`, B cache tokens, and B input above 272,000 tokens.
- **Prices.** One table, `prices-2026-10-28-r2`, per million tokens: `claude-sonnet-5` $2 input, $2.50 cache write, $0.20 cache read, $10 output; `gpt-6-sol` and `gpt-6.1-sol` $2 and $10.
- **One call at a time.** One process holds the ledger, at most one reservation is open, and a second send in flight is refused.

## Ledgers

Each budget has one ledger per mode, at a fixed place under the data root that every run root shares: `<data-root>/out/ledgers/<mode>/ledger-<budget>.jsonl`. Committed spend therefore adds up across run roots under one data root. Each entry extends a SHA-256 chain over the ledger's lines, and a mark (the ledger id, its last entry and that entry's chain link) records where a ledger stood. `<data-root>/out/ledgers/`, above the mode folders, holds the register `budgets.jsonl`, which lists every ledger created there, and `marks-<budget>.jsonl`, which gets the ledger's mark after every entry. Each run root keeps `ledger_marks-<budget>.jsonl`, written after each trajectory and by the reconcile and correct commands, and each `progress.json` carries the mark of its last entry.

Every command refuses a `--run-root` that is not a folder directly under `<data-root>/out`, other than `ledgers/` in any letter case, in fake and paid mode alike, so every start reads the marks of every run root under the data root. A ledger shorter than any of these marks, from the marks file or any run root, was rolled back or cut, and one that differs from a mark was replaced or edited; either is refused before anything is sent. So is a mark that names another ledger of the budget, unless the current ledger's header says it replaces that one. Once the register or a mark names a ledger for a budget, a second one, after the first was moved aside or deleted, is created only with `--new-budget-note`, which the new ledger's header keeps with the ids it replaces. `stage.json` names its ledger by budget, file name and id, never by an absolute path, and each run root's `run.json` holds a run id by which the ledger names the run wherever its folder is.

These checks hold within one data root while its register, its marks file or a run root that recorded a mark remains, so deleting the whole `<data-root>/out/ledgers` folder does not start a fresh cap while any run root that recorded a mark is left. The remaining gap is a copy of the whole data root, which carries copies of its ledgers and run roots that no local check can tell apart; the provider-side backstops, prepaid credits and spend limits, still apply.

## Paid mode

Paid mode needs `--paid`, `--confirm-paid-calls` (passed to the HTTPS transport as `confirm_paid_calls`) and `--approval-note`, an existing, non-empty file written after the mentor's written go-ahead, plus `--workspace` and `--openai-project`, the study's Anthropic workspace and OpenAI project. `ANTHROPIC_API_KEY` must be a key scoped to the study workspace: the HTTPS transport sends no `anthropic-workspace-id` request header, and [Anthropic's authentication page](https://platform.claude.com/docs/en/manage-claude/authentication#select-a-workspace), read on 2026-11-09, says a key not scoped to a workspace must name one in that header on every request and otherwise gets a 400 `invalid_request_error`. Such a key stops at the first count, as a `token_count` halt with nothing reserved. Every OpenAI request carries the project in its `OpenAI-Project` header, which the HTTPS transport adds at send time, so the prepared request, the example requests and the configuration hash do not depend on it; the header name comes from [OpenAI's API reference](https://developers.openai.com/api/reference/overview), read on 2026-11-08. A complete response that carries an `openai-project` header naming another project is a failed response check and halts the stage. That page lists no project header among its common response headers, so a response without one passes, and the request header and the reconciliation's project scope are what bind the calls to the project. A partial set of paid flags, or paid mode without both scopes, is refused before any transport exists. A paid stage without `--allocation` and `--allocation-sha256` is refused before any run folder exists. With none of the paid flags only the fake transport runs, with no API key read; the report says "every socket refused" only once the refusal hook is installed. `run.json`, `stage.json` and the report's settings record the workspace and project, and each reservation records its provider's scope, so a later stage or a resume under another `--workspace` or `--openai-project` is refused. Every run root shares the budget's ledger and one export covers one scope, so a run whose scope for a provider differs from one the ledger's reservations already name is also refused, before its `run.json` is written. `--approval-note`, `--panel-manifest`, `--allocation`, `--config-change-note` and `--export` must name files outside the repository.

## Token counts

Each reservation in paid mode is made at the provider's own count of the request it pays for. Before a trajectory is reserved, `HttpsTokenCounter` in [dispatch.py](../judge/dispatch.py) asks for one count per judge, since A1 to A3 send one body. A count goes out through the `HttpsTransport` that will send the request, so it has the send's API key, `anthropic-version` and `OpenAI-Project` header, and nothing retries behind the runner. Fake mode keeps the fake provider's count.

| | Anthropic | OpenAI |
|---|---|---|
| Endpoint | `POST https://api.anthropic.com/v1/messages/count_tokens` | `POST https://api.openai.com/v1/responses/input_tokens` |
| Left out of the sent body | `max_tokens`, `stream`, `inference_geo`, `service_tier` | `max_output_tokens`, `stream`, `prompt_cache_options`, `service_tier`, `store` |
| Count | `input_tokens` | `input_tokens`, with `object` set to `response.input_tokens` |
| Scope of the response | `anthropic-workspace-id` must be the study workspace | an `openai-project` header, when there is one, must be the study project |
| Stated cost of a count | free to use, under its own requests-per-minute limit | not stated |
| Read 2026-11-09 | [guide](https://platform.claude.com/docs/en/build-with-claude/token-counting), [reference](https://platform.claude.com/docs/en/api/messages/count_tokens), [overview](https://platform.claude.com/docs/en/api/overview) | [guide](https://developers.openai.com/api/docs/guides/token-counting), [reference](https://developers.openai.com/api/reference/resources/responses/subresources/input_tokens/methods/count), [pricing](https://developers.openai.com/api/docs/pricing) |

The fields left out are the ones each endpoint's reference does not list; neither reference says what happens to a field it does not list. Everything else stays, in the sent serialization and with its screenshots, and a request passes the request layer's body and leak checks before its count is asked for. Anthropic's guide calls its count an estimate that can differ from the actual input by a small amount; OpenAI's guide calls its count exact. OpenAI's guide, reference and pricing page state no price for a count, so its cost is not known; anything billed for one would appear in the usage export that the reconciliation reads. The send names no workspace header, so its API key must be scoped to the study workspace, as [paid mode](#paid-mode) says; a count is sent the same way and the workspace is read from its response, where a missing header fails. OpenAI's pages list no project response header, so a count without one passes, as a send does.

A count that fails, cannot be read, comes from another scope or holds no whole, positive `input_tokens` writes a `token_count` halt before anything of the trajectory is sent or reserved, and no estimate stands in. A transport failure, meaning no response, a cut response or any status the outcome table in [outcomes.py](../judge/outcomes.py) classes as TRANSPORT (a 408, a 429 rate limit, a 5xx, a 529, or another HTTP error that no halt rule names, such as a 409 or a 422), is asked again under the dispatcher's rule, at most three retries with its backoff; nothing else is asked again. After a correction note the resumed stage asks for the count again. The count is I in the reservation, and a B count above 272,000 is the `long_context` refusal under [spending rules](#spending-rules).

## Restart and reconciliation

Each ledger is append-only JSONL, each line fsynced before the next step, so a reservation is on disk before its request leaves. A torn last line, another budget or mode, or other pricing is refused. After a restart, an open reservation counts as spent until matched to its attempt record, or is held if none exists.

At each start the runner checks the ledger against the run root's records: every stage of the budget must have run on this ledger, every attempt they logged must have its reservation, and the ledger must not be shorter than, or differ from, any mark the run root recorded. Otherwise the ledger was rolled back or replaced, and nothing is sent. A slot folder holding a raw response without its attempt record, from a stop after the response was written, gets that record rebuilt from the raw bytes with the dispatcher's own classification, marked as recovered, and the call's reservation then closes from it, so no one reads the response to decide anything. An attempt can have two reservations, since a stop during its send leaves one held with no response and the next start reserves it again; the last one is the reservation that closes. The status was not kept. Bytes that start the provider's stream, or open with its error event, are taken as HTTP 200, so a complete stream is recorded as it was and a slot it ended is never sent again, and an error in the stream is classified as the dispatcher classified it. A provider error body is classified as the same error in a stream: a request, key, billing, permission, not-found or spend-limit error halts, with nothing resent until a note; a policy error on B is FILTERED and ends the slot; and a transient one is a transport failure. OpenAI marks some halting errors by the status alone, so a B error body that would otherwise be a transport failure halts unless it is a known transient error. A cut or unrecognized response is recorded as a transport failure whose slot is retried under the usual retry rule. The reservation of an OpenAI error body or error event is held until a passing reconciliation, that of an Anthropic one or of a cut or unrecognized response is held for good, and a complete stream's closes as it would have. The workspace and project headers were not kept either, so the record lists the provider's header check as not applied. A slot whose last attempt is a HALT with no halt record gets one at start and stays refused until a note.

The raw response is written before anything reads it, so a failure while it is read cannot lose a response that was paid for. If classifying a response or running its checks raises, or gives a value the attempt log cannot store, in the run or in a rebuild, the attempt is recorded with the halt kind `classification_error` and the stage stops until a note. A response that may be complete is MALFORMED, so its slot has ended and is never sent again: A1 stays fixed and the bytes stay in the log. An error status carries no model response, so that attempt is a HALT and its slot resumes with its next attempt after the note. Only the exception's type is recorded, since its message can quote the response. The reservation closes from the reported usage when that can be read and is held when pricing raises too. A halt record lost to a stop is written at the next start, as for a HALT. The one window left is a stop or a failed disk write before the raw file is on disk: the reservation is held and the slot is sent again.

`run_stage.py reconcile` reads a usage export in the runner's own format, not a provider's: CSV with the header `provider,model,input_tokens,cache_write_tokens,cache_read_tokens,output_tokens,cost_usd,period_start,period_end,scope`, or the same rows as JSON, with disjoint token counts; a larger `cost_usd` overrides the priced tokens. Token counts are priced at the table's base prices, so rows covering a call under a documented price modifier must give `cost_usd`. Each row states the export's period, in ISO 8601 with a time zone, and its scope, the Anthropic workspace or the OpenAI project, the same on every row of one provider; the reconcile entry records them. The export is cumulative from the ledger's creation and ends when it was taken. It is refused when:

- it has no rows for a provider that has any call in the ledger, even one whose calls all settled at zero; zero-token rows state that a provider billed nothing;
- a period starts after the ledger's `created_at`, ends before that provider's last settled or held call, or ends after the time of reconciliation;
- a scope is not the study's, as each reservation and the run's `run.json` record it;
- it is identical to an export reconciled before calls that were made since;
- a provider's total is more than 1% below the usage the ledger's own responses reported, which marks it as partial, stale or of another scope, or as pricing calls under a documented modifier at the base prices; the refusal names those calls. Anthropic's usage data typically appears within 5 minutes of a request, so export again once it is complete.

Usage above the ledger by more than 1% for either provider blocks every later call until `run_stage.py correct --budget` records a note. The note first settles, for each provider, an adjustment of the largest excess of the export over the ledger among the failed reconciliations since the last note, so after it committed spend is no longer below what the provider reported. Usage within the 1% tolerance passes with no adjustment.

A held reservation counts as spent in these checks and at the cap until it is released. A reconciliation that passes, with no failed one waiting for a note, appends a `release` entry for each OpenAI error still held, and that reservation settles at the cost the reconciliation establishes. An export gives one total per provider, so that cost is what the export bills above the ledger's known usage, meaning what the responses reported, adjustments and earlier releases: the whole excess, with no tolerance, given to the held calls in order, each up to its reservation, and $0 when the export shows no more than that usage. The 1% tolerance decides only whether a reconciliation passes. A failed or refused reconciliation releases nothing, so usage above the ledger goes through `correct --budget` first and the hold stays until a later reconciliation passes. Billing that reaches only a later export shows as usage above the ledger and goes the same way. Every other hold stays for good. A `release` entry is part of the hash chain, and on replay it must name a passing reconciliation after the hold, with no failed one waiting for a note, at no more than the reservation. A stop before a release leaves that call held for the next passing reconciliation.

In the evaluation, a trajectory does not start once the oldest settled or held call that no passing reconciliation follows is more than 23 hours old, so the daily rule never falls between A1 and its repeats; the refusal is a `reconcile_due` halt: reconcile, note the halt, and resume. A single call is refused at 24 hours as a backstop, and EVAL will not start or resume while such a call is more than 23 hours old.

## Dry run

`scripts/dry_run_stages.py` runs P1 to P3 through the fake transport at central and extreme token counts, reconciling after each stage, then repeats the extreme pilot on one ledger until the cap halts it. Each scenario keeps its ledger in its own `ledgers/` folder, apart from its run folders, which sit inside `--out`, since the dry run calls the runner's stage function rather than the stage command. The rubric is still a draft, so P3 runs there as a fake-mode rehearsal with the frozen-rubric rule waived, which the summary records; the runner itself never waives it. On the 19 development packs, central committed $16.83 and extreme $47.21; the repeated pilot halted at $94.50, its next $0.58 reservation refused.
